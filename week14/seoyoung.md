## 문제 1

### 문제 정보

* 문제명: 입국심사
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/43238
* 사용한 알고리즘 / 자료구조: 이분탐색(매개변수 탐색)

### 처음 접근 방식

심사관을 하나씩 비워지는 순서대로 배정하면 되겠다고 생각해서, 각 심사관의 "다음에 비는 시각"을 힙에 넣고 사람이 올 때마다 가장 빨리 비는 심사관에게 보내는 식으로 짰다. 예제는 전부 맞았는데 제출하니 시간초과가 났다. 사람이 10억 명까지 들어올 수 있어서 한 명씩 배정하는 구조 자체가 성립하지 않았다. 사람 수를 줄여볼 방법을 한참 찾다가, 애초에 "누가 어느 심사관에게 가는지"는 답에 필요 없고 걸린 시간만 물어본다는 걸 뒤늦게 봤다.

### 풀이 방법

1. 구할 값을 "모든 사람이 심사를 마치는 데 걸리는 시간"으로 두고, 이 값 자체를 탐색 대상으로 삼는다.
2. 하한은 1분, 상한은 `min(times) * n`으로 잡는다. 가장 빠른 심사관 한 명이 혼자 전부 처리해도 이 시간이면 끝나므로 답이 그보다 커질 수 없다.
3. 중간값 `mid`에 대해 "`mid`분 동안 처리 가능한 인원"을 `sum(mid // t for t in times)`로 구한다.
4. 처리 가능한 인원이 `n` 이상이면 `mid`는 충분한 시간이므로 답 후보로 저장하고 상한을 `mid - 1`로 내린다.
5. `n`보다 적으면 시간이 모자라므로 하한을 `mid + 1`로 올린다.
6. 하한이 상한을 넘을 때까지 반복하고, 저장해둔 후보 중 가장 작은 값을 반환한다.

### 어려웠던 지점

"답을 이분탐색한다"는 발상 자체가 제일 안 잡혔다. 그동안 이분탐색은 정렬된 배열에서 값을 찾는 도구라고만 생각했는데, 여기선 탐색할 배열이 아예 없었다. 상한을 어떻게 잡아야 하는지도 막막해서 처음엔 대충 `10**18`을 넣었다가 반복 횟수가 쓸데없이 늘었다. 구현에서는 `while low <= high`와 `while low < high`를 섞어 쓰다가 마지막 한 칸에서 무한루프에 빠졌고, 조건을 만족할 때 `high = mid`로 둘지 `high = mid - 1`로 둘지도 헷갈렸다.

### 해결 방법

"시간 `t`로 가능한가?"라는 질문의 답이 `t`가 커질수록 거짓에서 참으로 한 번만 바뀐다는 점을 확인하고 나니 이분탐색을 쓸 수 있는 이유가 납득됐다. 가능/불가능이 뒤섞여 있으면 못 쓰지만, 한 번만 뒤집히면 그 경계를 찾는 문제가 된다. 경계 처리는 `while low <= high`에 `high = mid - 1` 조합으로 고정하고 답을 따로 변수에 저장하는 방식으로 통일했다. 이렇게 하면 루프가 반드시 끝나고 마지막에 답 변수에 최소 참값이 남는다. 상한은 `min(times) * n`으로 줄여서 반복을 10번 가까이 아꼈다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(M log(min(times) * n))
* 공간복잡도: O(1)

`M`은 심사관 수(최대 100,000), `n`은 사람 수(최대 1,000,000,000)다. 이분탐색 반복이 약 60회이고 매번 심사관 전체를 훑어 처리 인원을 세므로 `O(M)`이 곱해진다. 추가로 쓰는 공간은 변수 몇 개뿐이다.

### 새롭게 알게 된 점

구하려는 답이 숫자 하나이고, 그 값에 대해 "이 값이면 되는가?"를 빠르게 판정할 수 있으며, 판정 결과가 한 번만 뒤집히면 답을 범위로 두고 이분탐색할 수 있다는 걸 알게 됐다. 이게 매개변수 탐색이라고 불린다는 것도 이번에 정리했다. 13주차 표 편집에서 "삭제를 실제로 하지 말고 연결만 바꾼다"고 관점을 틀었던 것처럼, 이번에도 "사람을 배정하지 말고 시간을 추측한다"로 질문을 바꾸니 크기 제한이 문제가 되지 않았다. 입력 범위가 10억처럼 터무니없이 크면 하나씩 세는 풀이는 애초에 의도가 아니라는 신호로 읽어야겠다.

## 문제 2

### 문제 정보

* 문제명: 이중우선순위큐
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/42628
* 사용한 알고리즘 / 자료구조: 힙(우선순위 큐) 두 개, 지연 삭제

### 처음 접근 방식

최솟값과 최댓값을 둘 다 빼야 하니 그냥 리스트에 넣고 삭제할 때마다 `min`이나 `max`를 찾아 지우면 되겠다고 생각했다. 연산이 최대 1,000,000개라 매번 전체를 훑는 건 느릴 게 뻔했다. 그다음엔 리스트를 정렬 상태로 유지해서 양 끝에서 빼려고 했는데, 삽입할 때마다 자리를 찾아 밀어 넣어야 해서 삽입이 `O(N)`이 됐다. 파이썬 `heapq`는 최소 힙만 제공하니 최댓값을 못 빼는 것도 걸림돌이었다.

### 풀이 방법

1. 최소 힙 `min_heap`과 최대 힙 `max_heap`을 둔다. 최대 힙은 값에 `-1`을 곱해 넣어 최소 힙으로 흉내 낸다.
2. 값이 실제로 살아 있는지 표시할 `alive` 배열(또는 딕셔너리)을 두고, 삽입 순서대로 매긴 고유 번호를 키로 쓴다.
3. 삽입 `I n`이면 새 번호를 붙여 `(값, 번호)`를 두 힙 모두에 넣고 `alive[번호] = True`로 둔다.
4. 삭제 `D 1`이면 `max_heap`의 꼭대기를 보되, `alive`가 거짓인 항목은 이미 반대쪽에서 지워진 것이므로 버리고 다음을 본다. 살아 있는 항목이 나오면 꺼내고 `alive`를 거짓으로 바꾼다.
5. 삭제 `D -1`이면 같은 방식으로 `min_heap` 쪽에서 처리한다.
6. 큐가 비어 있으면 삭제 연산은 무시한다. 모든 연산이 끝나면 두 힙에서 죽은 항목을 걷어낸 뒤, 비었으면 `[0, 0]`을, 아니면 `[최댓값, 최솟값]`을 반환한다.

### 어려웠던 지점

힙을 두 개 쓰면 한쪽에서 지운 값이 다른 쪽에는 그대로 남는다는 게 핵심 문제였다. 처음엔 삭제할 때 반대쪽 힙에서도 그 값을 찾아 지우려 했는데, 힙 중간에서 특정 원소를 지우는 건 `O(N)`이라 두 개를 쓰는 의미가 없어졌다. 값이 중복될 수 있다는 점도 놓쳐서, 같은 숫자가 두 번 들어왔을 때 하나만 지워야 하는데 둘 다 사라지는 버그가 났다. 그리고 "큐가 비어 있으면 무시"를 빼먹어서 빈 힙에서 `pop`을 하다 예외가 났다.

### 해결 방법

"지울 때 바로 지우지 말고, 꺼낼 때 유효한지 확인한다"로 방향을 바꿨다. 반대쪽 힙에 남은 항목은 어차피 꼭대기로 올라왔을 때만 보게 되고, 그때 죽은 항목이면 그냥 버리면 된다. 버려지는 항목은 하나당 최대 한 번만 버려지므로 전체 비용이 늘지 않는다. 중복 값 문제는 값만 비교하지 말고 삽입 순서 번호를 같이 저장해 `(값, 번호)` 단위로 다루니 해결됐다. 같은 숫자여도 번호가 다르니 서로 다른 항목으로 구분된다. 빈 큐 처리는 삭제 분기 맨 앞에 살아 있는 항목 수를 세는 변수를 확인하는 줄을 넣어 막았다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(K log K)
* 공간복잡도: O(K)

`K`는 연산의 개수(최대 1,000,000)다. 삽입은 힙 두 개에 넣으므로 `O(log K)`이고, 삭제에서 죽은 항목을 걷어내는 반복은 항목 하나당 평생 한 번만 일어나므로 전체를 합쳐도 `O(K log K)`를 넘지 않는다. 두 힙과 `alive` 배열이 각각 연산 수에 비례하는 공간을 쓴다.

### 새롭게 알게 된 점

같은 데이터를 서로 다른 기준으로 정렬된 자료구조 두 개에 중복 저장하고, 동기화는 포기하는 대신 꺼낼 때 검증하는 패턴을 알게 됐다. 지연 삭제라고 부르는 방식인데, "정확하게 맞춰두기"보다 "틀린 걸 나중에 걸러내기"가 더 싼 경우가 있다는 게 새로웠다. 13주차 주차 요금 계산에서 누적과 계산 단계를 분리했던 것과 비슷하게, 여기서도 삭제와 반영 시점을 분리한 셈이다. 그리고 파이썬 `heapq`로 최대 힙이 필요할 땐 부호를 뒤집는다는 것, 튜플을 넣으면 앞 원소부터 차례로 비교한다는 것도 함께 챙겼다.

## 문제 3

### 문제 정보

* 문제명: 보석 쇼핑
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/67258
* 사용한 알고리즘 / 자료구조: 투 포인터(슬라이딩 윈도우), 해시(딕셔너리)

### 처음 접근 방식

모든 구간을 다 만들어 보고 그 안에 보석 종류가 전부 들어 있는지 확인하려고 했다. 시작점과 끝점을 이중 반복문으로 돌리고 구간마다 `set`을 만들어 종류 수를 셌다. 진열대 크기가 100,000이라 구간 개수만 50억에 가까워서 당연히 시간초과였다. 구간 안의 종류 수를 매번 다시 세는 것도 낭비라, 끝점을 하나 늘릴 때 이전 결과를 재활용할 방법을 찾기 시작했다.

### 풀이 방법

1. 전체 보석 종류 수를 `set(gems)`의 크기로 구해 `total`에 저장한다.
2. 왼쪽 포인터 `left`를 0에 두고, 구간 안의 보석별 개수를 담을 `count` 딕셔너리를 준비한다.
3. 오른쪽 포인터 `right`를 0부터 끝까지 옮기면서 `gems[right]`의 개수를 1 늘린다.
4. 구간에 담긴 종류 수가 `total`과 같아지면, 그 구간은 조건을 만족하므로 왼쪽을 줄일 수 있는 만큼 줄인다.
5. 줄이는 조건은 `count[gems[left]] > 1`, 즉 맨 왼쪽 보석이 구간 안에 또 있는 경우다. 이때 개수를 1 줄이고 `left`를 한 칸 옮긴다.
6. 더 줄일 수 없게 되면 현재 구간 길이를 지금까지의 최솟값과 비교해 갱신한다. 길이가 같으면 시작 위치가 더 앞선 쪽을 남긴다.
7. 반복이 끝나면 저장해둔 구간을 1부터 세는 번호로 바꿔 `[시작, 끝]`으로 반환한다.

### 어려웠던 지점

왼쪽 포인터를 언제 움직여야 하는지가 가장 헷갈렸다. 처음엔 종류 수가 다 찼을 때 무조건 왼쪽을 한 칸 밀었는데, 그러면 방금 유일하게 하나뿐이던 보석을 버려서 조건이 깨지는데도 길이를 갱신해버렸다. 반대로 너무 조심스럽게 짜서 왼쪽을 아예 안 움직이면 최소 구간이 안 나왔다. 그리고 답이 여러 개일 때 가장 짧은 것, 그중에서도 시작이 빠른 것을 골라야 하는데 `<=`로 비교하는 바람에 뒤쪽 구간으로 덮어써서 틀렸다. 인덱스를 0부터 세다가 1부터 세는 번호로 바꾸는 것도 마지막에 빼먹었다.

### 해결 방법

왼쪽을 미는 조건을 "조건이 깨지지 않는 한에서만"으로 정확히 못박았다. 맨 왼쪽 보석의 개수가 2 이상이면 하나 버려도 그 종류는 구간에 남으니 안전하고, 1이면 그게 마지막 하나라 버리는 순간 조건이 깨지므로 멈춘다. 이 한 줄 조건으로 "유효한 구간 중 가장 짧은 것"이 자연스럽게 나왔다. 길이 비교는 `<`만 쓰도록 고쳐서, 같은 길이면 먼저 찾은 쪽(시작이 더 앞선 쪽)이 유지되게 했다. 오른쪽 포인터가 왼쪽으로 돌아가는 일이 없으니 두 포인터 모두 배열을 한 번씩만 지나간다는 것도 확인했다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(N)
* 공간복잡도: O(N)

`N`은 진열대의 보석 개수(최대 100,000)다. `right`는 처음부터 끝까지 한 번 이동하고 `left`도 되돌아가지 않으므로 둘의 이동 횟수를 합쳐도 `2N`을 넘지 않는다. 딕셔너리에는 보석 종류 수만큼의 항목이 들어가고 최악의 경우 모두 다른 종류라 `O(N)`이다.

### 새롭게 알게 된 점

"조건을 만족하는 가장 짧은 구간"류 문제는 구간을 전부 만들지 않고, 오른쪽으로 늘려 조건을 맞춘 뒤 왼쪽을 당겨 군더더기를 깎는 식으로 접근한다는 걸 알게 됐다. 핵심은 왼쪽 포인터가 절대 되돌아가지 않는다는 점이고, 그래서 이중 반복문처럼 보여도 전체가 선형이다. 이 문제를 풀고 나서 11주차에 풀었던 호텔 대실을 다시 보니, 그때는 구간을 정렬해서 처리했지만 이번엔 포인터 두 개로 구간을 직접 움직인다는 차이가 눈에 들어왔다. 그리고 구간 안의 상태를 `set`으로 매번 새로 만들지 말고 딕셔너리 카운트로 들고 다니며 갱신하면, 들어오고 나가는 원소만 손대면 된다는 것도 정리됐다.
